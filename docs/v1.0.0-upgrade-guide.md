# Upgrade Guide: v0.4.x to v1.0.0

- [`regions[*].shard_number` removed (Breaking Change)](#regionsshard_number-removed-breaking-change)
- [`frequencies` to copy policy items (Breaking Change)](#frequencies-to-copy-policy-items-breaking-change)

## `regions[*].shard_number` removed (Breaking Change)

v1.0.0 removes `regions[*].shard_number`, which v0.4.0 deprecated in favor of `regions[*].shard_name`. Use `shard_name` for all SHARDED and GEOSHARDED shard grouping.

Terraform silently drops an attribute that is no longer part of an object-typed variable. The module cannot reject a stale `shard_number`, so leaving it in place does not raise a "field removed" error. Instead, the region loses its explicit shard identity and the plan changes, which can reduce the shard count for a GEOSHARDED zone. Migrate your shard identities before you upgrade.

### Who is affected?

Deployments that set `shard_number` on any region for SHARDED or GEOSHARDED grouping. This change does not affect configs that use `shard_count` (uniform shards) or replica sets.

### Required action

Replace every `shard_number = N` with a `shard_name` that matches `^[a-z0-9]{1,24}$`. Keep the same grouping and list order to make the upgrade a no-op plan.

```terraform
# Before (v0.4.x, shard_number deprecated)
regions = [
  { name = "US_EAST_1", node_count = 3, shard_number = 0 },
  { name = "US_WEST_2", node_count = 3, shard_number = 1 },
]

# After (v1.0.0)
regions = [
  { name = "US_EAST_1", node_count = 3, shard_name = "0" },
  { name = "US_WEST_2", node_count = 3, shard_name = "1" },
]
```

What happens if you do not migrate:

- SHARDED explicit configs fail at plan. With no `shard_name`, the module reports that every region must set `shard_name` (or use `shard_count`). The plan does not apply.
- GEOSHARDED configs can change silently. A zone whose regions all relied on `shard_number` now has no explicit identity, so the module treats the zone as a single default shard and collapses multiple shards per zone into one `replication_specs` entry. Terraform then plans to remove shards. Migrate to `shard_name` before upgrading to avoid this.

For a GEOSHARDED configuration, each `shard_name` must map to one shard within one zone. Regions that share the same shard in a single zone can share a `shard_name`, but you must not reuse that `shard_name` in any other zone. If you set zone-scoped `shard_number = 0` in multiple zones, you cannot use `"0"` as the `shard_name` for these zones. Instead, assign distinct names per zone (for example, `"us0"` and `"eu0"`).

```terraform
# Before (v0.4.x): zone-scoped shard_number, reused across zones
regions = [
  { name = "US_EAST_1", node_count = 3, zone_name = "US", shard_number = 0 },
  { name = "EU_WEST_1", node_count = 3, zone_name = "EU", shard_number = 0 },
]

# After (v1.0.0): distinct shard_name per zone
regions = [
  { name = "US_EAST_1", node_count = 3, zone_name = "US", shard_name = "us0" },
  { name = "EU_WEST_1", node_count = 3, zone_name = "EU", shard_name = "eu0" },
]
```

Ordering is unchanged by migration: both `shard_number` and `shard_name` groups follow first appearance in `regions`. Reorder the list if you need a specific `replication_specs` sequence.

### Why the change?

Numeric shard grouping was ambiguous in GEOSHARDED clusters because `shard_number` was zone-scoped, so the same number meant different shards in different zones. `shard_name` is a single cluster-wide identifier that must be unique across zones, which removes the ambiguity.

### State migration

None. `shard_number` and `shard_name` are module-only grouping keys and are not stored as Atlas shard identity. Migrating to `shard_name` with the same grouping and order produces the same `replication_specs`, so no state migration is required and the plan stays a no-op.

## `frequencies` to copy policy items (Breaking Change)

The `cloud_backup_schedule` submodule no longer writes the deprecated `frequencies` list on each `copy_settings` entry. When `backup_copy_region` is set, it now writes `copy_policy_items` (derived from `backup_retention`) or `last_number_of_snapshots`, and sets `copy_policy_items_enabled = true` on the schedule.

### Who is affected?

Deployments that set `backup_copy_region` (cross-region snapshot copies). Configs without a copy target are unaffected.

### Required action

None. No variable changed name or shape for an existing copy target, so an existing config applies unchanged. The module switches the schedule from `frequencies` to copy policy items on the next apply.

### What changes in the plan

The switch is one-way: after Atlas enables copy policy items for a cluster, it cannot be turned off, so the schedule keeps `copy_policy_items_enabled = true` from then on. Existing callers see the switch as an in-place update on their next apply. By default each copy policy item mirrors the source frequency's retention, so the copies keep the coverage they had under `frequencies`.

To stop cross-region copying after this switch, set `backup_copy_region = { region_count = 0 }`: the module keeps `copy_policy_items_enabled = true` and sends an empty `copy_settings`, which Atlas accepts. Removing `backup_copy_region` outright does not work: the module sends `copy_policy_items_enabled = false` and Atlas rejects the request, so the apply fails until a copy target is restored.

### Why the change?

`frequencies` is deprecated by the provider and the Atlas Admin API. Copy policy items are its successor and add per-frequency copy retention (`backup_retention[*].copy_retention_value`), count-based copies (`backup_copy_region.last_number_of_snapshots`), and the `update_copy_snapshots`/`delete_copy_snapshots` lifecycle flags.

### New copy targets are additive

`backup_copy_region.region_count`, `backup_copy_region.regions`, and the copy-policy-item fields are opt-in. The default (`backup_copy_region = {}`) still derives one target, so no existing config gains extra copies without asking for them.
