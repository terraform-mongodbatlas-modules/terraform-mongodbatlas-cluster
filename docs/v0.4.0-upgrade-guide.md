# Upgrade Guide: v0.3.x to v0.4.0

This guide covers behavior changes when upgrading to v0.4.0 of the MongoDB Atlas Cluster module. The module remains in public preview; treat upgrades as you would any pre-v1 module.

- [TLS minimum protocol default under RECOMMENDED (Breaking Change)](#tls-minimum-protocol-default-under-recommended-breaking-change)
- [Breaking change: New config server management mode default](#breaking-change-new-config-server-management-mode-default)

## TLS minimum protocol default under RECOMMENDED (Breaking Change)

v0.4.0 adds `default_feature_set` (`RECOMMENDED` | `STANDARD`, default `RECOMMENDED`) and sets `advanced_configuration.minimum_enabled_tls_protocol` to `TLS1_3` when you use `RECOMMENDED` and omit that attribute. Under `STANDARD`, the module leaves the attribute unset unless you set it explicitly.

### Why the change?

TLS 1.3 is the recommended minimum protocol. `default_feature_set` lets future recommended defaults ship the same way without forcing every caller onto new behavior.

### Who is affected?

Users who omit `default_feature_set` and omit `advanced_configuration.minimum_enabled_tls_protocol` (they get `RECOMMENDED`). After upgrading, `terraform plan` may show an in-place update from `TLS1_2` to `TLS1_3`.

Users who already set an explicit TLS protocol are not affected.

Users who set `default_feature_set = "STANDARD"` and omit TLS are not affected for this field: the attribute is Optional+Computed, so Terraform keeps the existing state value with no plan change.

### Required action

-> IMPORTANT: This is more than a Terraform plan change. Raising the minimum to `TLS1_3` makes the cluster reject clients that can only negotiate TLS 1.2, so accepting the default can cause an application outage. Before you accept the plan, verify that every client runtime and driver that connects to the cluster supports TLS 1.3 (check driver versions, OpenSSL/TLS library versions, and any proxies or connection poolers in the path).

Once you have confirmed all clients support TLS 1.3, accept the plan. If you cannot confirm this (or any client is limited to TLS 1.2), keep `TLS1_2` pinned using a zero-diff option below and upgrade to TLS 1.3 later.

### Zero-diff option

Before upgrading, choose one of the following:

1. Set `default_feature_set = "STANDARD"` to opt out of the TLS 1.3 default (and future recommended defaults). TLS stays unset in config; existing state is preserved.
2. Set an explicit `advanced_configuration.minimum_enabled_tls_protocol` to pin the value (for example `TLS1_2`) while staying on `RECOMMENDED` for future defaults.

```terraform
module "cluster" {
  source  = "terraform-mongodbatlas-modules/cluster/mongodbatlas"
  version = "~> 0.4"

  project_id   = var.project_id
  name         = var.name
  cluster_type = "REPLICASET"
  regions      = var.regions

  # Option 1: opt out of new recommended defaults
  default_feature_set = "STANDARD"

  # Option 2: pin TLS while staying on RECOMMENDED
  # advanced_configuration = {
  #   minimum_enabled_tls_protocol = "TLS1_2"
  # }
}
```

No state migration is required. This is an in-place attribute update only.

## Breaking change: New config server management mode default

Starting in v0.4.0, `config_server_management_mode` defaults to `ATLAS_MANAGED` instead of `null`. In `ATLAS_MANAGED` mode, Atlas automatically transitions the cluster between an embedded config server and a dedicated config server based on shard count, and Terraform does not report these transitions as configuration drift. To pin the cluster to a dedicated config server and prevent automatic transitions, set `config_server_management_mode` to `FIXED_TO_DEDICATED`.

### Why the change?

When `config_server_management_mode` is `null`, Atlas can still transition the cluster's `config_server_type` server-side. Because Terraform tracks `config_server_type`, the next `terraform plan` reports that server-side transition as drift. An explicit `ATLAS_MANAGED` default matches Atlas-managed behavior and keeps that churn out of `terraform plan`.

### Which clusters are affected?

`SHARDED` and `GEOSHARDED` clusters that omit `config_server_management_mode` are affected. After upgrading, `terraform plan` may show an in-place update that sets `config_server_management_mode` to `ATLAS_MANAGED`.

`REPLICASET` clusters are not affected. The module sends `config_server_management_mode = null` for replica sets, which Terraform treats the same as leaving it unset.

Clusters that already set `config_server_management_mode` to `ATLAS_MANAGED` or `FIXED_TO_DEDICATED` are not affected.

### Required action

Accept the plan if Atlas-managed config servers are acceptable, or use the zero-diff option below before upgrading.

### Zero-diff option

Before upgrading, set `config_server_management_mode = null` to keep the previous unset behavior and avoid a plan change:

```terraform
module "cluster" {
  source  = "terraform-mongodbatlas-modules/cluster/mongodbatlas"
  version = "~> 0.4"

  project_id   = var.project_id
  name         = var.name
  cluster_type = "SHARDED"
  regions      = var.regions

  config_server_management_mode = null
}
```

To pin the cluster to a dedicated config server and prevent automatic transitions, set `config_server_management_mode = "FIXED_TO_DEDICATED"` instead.

No state migration is required. Accepting the new default is an in-place attribute update only.
